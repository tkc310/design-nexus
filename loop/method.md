# 手法の改善ログ

改善ループそのもの(ケース、審査、判定、手順)の変更を記録します。スキルの変更は `experiments.md` に書きます。各実験の後に「手法の振り返り」(`IMPROVEMENT.md` の手順5)を行い、手法を変えたらここに1エントリ足します。

## テンプレート

```
### M-NNN タイトル
- date:
- trigger: (どの実験の何がきっかけか)
- problem: (手法のどこが、誤った信号や無駄を生んだか)
- change: (何をどう変えたか)
- check: (次の実験で、効いたかをどう確かめるか)
```

### M-008 対比較の審査(新旧のページを並べて選ぶ)
- date: 2026-11-01
- trigger: EXP-014〜021 で採用は1件。狙った欠陥は消えるのに合計が動かず、同じ品質帯の run で Sonnet の平均が 49.6〜52.4 動くなど、絶対点(0〜4)の審査のぶれが効果より大きかった
- problem: 絶対点は、審査のその日の基準(甘さ・辛さ)をそのまま含む。base と候補を別々の審査が採点するので、基準のずれが差に入る。
- change:
  - `pair --base <run> --run <候補>` が、ケースと base run ごとに `PAIR_PROMPT.md`(`eval/pair-prompt.md` + ブリーフ + 2つのページ)を `_pairs/` に書く。A/B の並びは id のハッシュで決め、`_pairs/key.json` に記録する(審査は開かない)。`--swap` は逆順の対も書く。
  - 審査は同じ4人の審査団で、次元ごとと全体で A・B・tie を選び、差の大きさ(slight / clear / large)と決め手を書く(`pair.<model>.json`)。
  - `pair-score` が候補から見た勝ち・負け・引き分けを、審査ごと、ケースごと、次元ごとに数える。両順で審査した対は、順で判定が変わったら引き分けにする。margin が clear 以上の判定だけを数えた列も出す。
- check(v0.7.1 の run A を候補に、12対 × 両順 × Opus・Sonnet の48判定):
  - 差があるはずの対(v0.3.0 の run、絶対点で約5点低い): 両順の一致だけ数えて Opus 5–1–0、Sonnet 3–2–1。順で判定が変わったのは12組中1組。
  - 差がないはずの対(同じ v0.7.1 の run B): Opus 0–3–3、Sonnet 1–3–2。12組中5組が順で変わった。
  - 位置の偏り: 片順だけの Opus は、差がない対で6件中5件 A を選んだが、48判定の合計では A 24・B 24 で、偏りは近い差の判定(slight)に出る。
  - 順で変わった6組は、すべて両順とも slight だった。clear 以上の判定は、逆順でも必ず同じ側を選んだ。clear 以上だけを数えると、差がある対は Opus 3–0、Sonnet 2–0、差がない対は両方 0–0。
  - Opus と Sonnet は、clear の判定ではすべて同じ側を選んだ。差がない対でも、03 と 06 では両方の審査が両順で run B を選んだ。同じスキルの2回の生成のあいだに、審査がそろって見分けられる本物の差がある(生成のばらつき、M-005)。
- 結論: 対比較は位置の偏りを slight の判定に閉じ込めれば使える。差の大きい変更は確実に見分けるが、生成のばらつきは減らせないので、+1〜+2 点の効果を1回の生成で判定できるようにはならない。絶対点はスコアの記録に残し、採用判定の境界(`eval/rubric.md` 規則6)で対比較を使う。片順の審査で clear 以上だけを数えれば、両順と同じ判定になり、費用は半分で済む。
