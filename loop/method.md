# 手法の改善ログ

改善ループそのもの(ケース、審査、判定、手順)の変更を記録します。スキルの変更は `experiments.md` に書きます。各実験の後に「手法の振り返り」(`IMPROVEMENT.md` の手順5)を行い、手法を変えたらここに1エントリ足します。

## テンプレート

```
### M-NNN タイトル
- date:
- trigger: (どの実験の何がきっかけか)
- problem: (手法のどこが、誤った信号や無駄を生んだか)
- change: (何をどう変えたか)
- check: (次の実験で、効いたかをどう確かめるか)
```

## エントリ

### M-001 検証用ケース、審査パネル、主審査、base の自動再採点
- date: 2026-10-31
- trigger: EXP-001〜004 の振り返り
- problem:
  - 仮説の発見と効果の確認を同じ6件で行っていたので、この6件への過剰適合を見分けられなかった。
  - 合計点の伸びの大半が、甘い審査(EXP-003 では Sonnet +4.0、Opus +0.7)から来ていた。3者の平均だけで判定すると、厳しい審査が見た悪化が隠れる。
  - 審査プロンプトが1人の審査員だったので、ブランド・操作・レイアウト・アクセシビリティのどれを重く見るかが審査ごとに揺れた。
  - EXP-004 では、新しいチェックで base を手作業で採点し直す必要があった。忘れると、チェックの追加が「悪化」に見える。
  - 生成役が Sonnet だったので、スキルの上限ではなくモデルの上限を測っていた可能性がある。
- change:
  - 検証用ケースを6件追加し(07〜12、`split: holdout`)、`prepare --split` で選べるようにした。仮説と判定には学習用(01〜06)だけを使う。
  - 審査を熟練デザイナー4人のパネルにした(`eval/judge-prompt.md`、`eval/rubric.md`)。
  - Opus を主審査とし、`compare` で主審査の平均が −1 点を超えて下がったら不採用にする(`--primary`)。Fable と Sonnet は並列審査。
  - `compare` が base を現在のチェックで自動的に採点し直す(`--rescore no` で無効)。
  - 計画・生成・最終評価を Opus で行う。12件を新しい基準として測り直す。
- check: 新しい基準の run で、審査3者の差(甘さの偏り)と、ケースごとのばらつきを記録する。次の実験で、主審査と並列審査の向きが一致するかを見る。

### M-002 独立した仮説を並列に試す、審査の盲検性
- date: 2026-10-31
- trigger: 新しい基準の run と、ユーザーからの「やり方自体も改善してループする」という依頼
- problem:
  - 1実験ごとに生成と審査を直列に回すと、1周に1時間近くかかる。互いに独立した仮説も順番待ちになる。
  - 審査が `index.html` を開かずに、スクリーンショットと NOTES だけで採点することがあった(Sonnet、07〜12)。D8 と D10 はコードを見ないと判断できない。
  - ケースのフォルダには `score.json` があり、ほかの審査の点数が入りうる。盲検性が崩れる。
  - render-check が、グローバルにインストールされた Playwright を `NPM_GLOBAL` なしでは見つけられなかった(生成役2件が手で環境変数を設定した)。
- change:
  - 互いに独立した仮説は、同じ基準から別々のスキルの写し(`prepare --skill <dir>`)で並列に試す。和文のように対象が限られる仮説は、該当するケースだけで回す(`--cases`)。採用したものは本体に統合し、次の基準 run で合わせて確かめる。
  - render-check は `npm root -g` も探す(修正済み)。
  - 審査プロンプトの改善(コードを読むことの義務化、ほかの審査結果を読まない)は、この回の実験の後に入れる。途中で変えると、基準と候補で審査条件がずれるため。
- check: 並列の3実験で、仮説ごとに狙った次元が動くか。統合した版で、効果が足し算になるかを次の基準 run で見る。
