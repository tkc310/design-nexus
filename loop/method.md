# 手法の改善ログ

改善ループそのもの(ケース、審査、判定、手順)の変更を記録します。スキルの変更は `experiments.md` に書きます。各実験の後に「手法の振り返り」(`IMPROVEMENT.md` の手順5)を行い、手法を変えたらここに1エントリ足します。

## テンプレート

```
### M-NNN タイトル
- date:
- trigger: (どの実験の何がきっかけか)
- problem: (手法のどこが、誤った信号や無駄を生んだか)
- change: (何をどう変えたか)
- check: (次の実験で、効いたかをどう確かめるか)
```

## エントリ

### M-002 独立した仮説を並列に試す、審査の盲検性
- date: 2026-10-31
- trigger: 新しい基準の run と、ユーザーからの「やり方自体も改善してループする」という依頼
- problem:
  - 1実験ごとに生成と審査を直列に回すと、1周に1時間近くかかる。互いに独立した仮説も順番待ちになる。
  - 審査が `index.html` を開かずに、スクリーンショットと NOTES だけで採点することがあった(Sonnet、07〜12)。D8 と D10 はコードを見ないと判断できない。
  - ケースのフォルダには `score.json` があり、ほかの審査の点数が入りうる。盲検性が崩れる。
  - render-check が、グローバルにインストールされた Playwright を `NPM_GLOBAL` なしでは見つけられなかった(生成役2件が手で環境変数を設定した)。
- change:
  - 互いに独立した仮説は、同じ基準から別々のスキルの写し(`prepare --skill <dir>`)で並列に試す。和文のように対象が限られる仮説は、該当するケースだけで回す(`--cases`)。採用したものは本体に統合し、次の基準 run で合わせて確かめる。
  - render-check は `npm root -g` も探す(修正済み)。
  - 審査プロンプトの改善(コードを読むことの義務化、ほかの審査結果を読まない)は、この回の実験の後に入れる。途中で変えると、基準と候補で審査条件がずれるため。
- check: 並列の3実験で、仮説ごとに狙った次元が動くか。統合した版で、効果が足し算になるかを次の基準 run で見る。

### M-003 主審査のぶれを測る、比較を共通ケースにそろえる
- date: 2026-10-31
- trigger: EXP-005〜008 の振り返り
- problem:
  - `compare` が、base の全12件の平均と候補の3件や6件の平均を比べていた。EXP-007 は「87.4 → 88.0(+0.6)」と表示されたが、共通3件で比べると 89.7 → 88.0(−1.7)だった。
  - 主審査 Opus の「−1 点で不採用」という規則が、1回の採点のぶれより小さい差を見ていた。同じページを Opus で2回採点すると、ケースごとに最大 4.8 点(60点満点)、base 6件の平均で 2.4 点ずれた(48.8 と 46.4)。EXP-005 は1回目の主審査が −1.1 で不採用になるところだったが、2回の平均では +0.6 だった。
  - 審査役どうしが同じ切り抜き画像の置き場所を使い、互いのファイルを上書きしていた。
  - 9体以上のエージェントを同時に動かすと、利用上限(5時間枠)に達して全員が止まった。止まったエージェントは、上限が戻ってから続きを再開できた。
- change:
  - `compare` は、両方の run にあるケースだけで平均と次元を比べる。
  - 同じモデルの繰り返し採点(`judge.opus.2.json`)は、まずモデルごとに平均してから、モデル間で平均する。
  - 主審査の差が −1〜−2.5 の境界にあり、ほかの条件を満たすときは、base と候補の両方を主審査でもう1回採点し、2回の平均で判定する(`eval/rubric.md` 規則5)。
  - 審査役ごとに別の切り抜き用フォルダを指定し、`index.html` を全部読むよう指示する。
  - 同時に動かすエージェントは、生成と審査を合わせて10体程度までにする。
- check: base の主審査は2回分の平均を持つようになった。今後の候補が1回だけの主審査で境界に入る頻度と、再採点で判定が変わる頻度を記録する。
- 未対応: R18 が、表示中に時刻が変わる時計を「320 で消えた文」と誤検出する(EXP-008 の 04)。a11y 専門家の上限2点が、小さな組版の欠陥にも効きすぎている可能性(和文の改行)。

### M-004 専門家の拒否権を2段階にし、和文の改行を JLReq で判断する
- date: 2026-10-31
- trigger: EXP-007、EXP-010 の不採用と、EXP-005〜010 の全審査の振り返り
- problem:
  - 和文の3件(02・03・05)では、ほぼすべての審査で D4 が2点に抑えられていた。理由は「本文が語の途中で折れる」。EXP-007(auto-phrase を全体に適用)と EXP-010(R19 で残りを列挙して直す)は、改行を減らしたが、審査は残りの1か所を見つけて同じく2点にした。スキル側をどう変えても動かない次元は、改善の信号にならない。
  - 審査プロンプトは、専門家の「具体的な欠陥」なら何でも上限2点にしていた。WCAG 違反と組版の小さな傷が同じ重さだった。
  - 日本語組版の標準(W3C JLReq)では、本文の仮名・漢字の間での改行は正しい組版で、禁止されるのは行頭・行末の禁則などに限られる。審査プロンプトの「改行と文節分割」は、この標準より厳しい、欧文の慣習に近い基準だった。
- change:
  - 専門家の拒否権を2段階にした。WCAG 2.2 AA 違反、または内容が読めない・誤読される欠陥は上限2点。組版の小さな傷は、目立つ場所か繰り返しのときだけ1点下げる。
  - 和文の改行は JLReq で判断する。欠陥は、禁則違反、数字と単位の分離、見出し・ボタン・ラベルなど1〜2行のテキストでの語の分割、見出しの1〜2字の最終行。
  - 審査条件が変わったので、新しい基準(v0.4.0 の生成)を作り、旧基準(v0.3.0)も同じプロンプトで審査し直して比べる。旧プロンプトの点数とは直接比べない。
- check: 新しいプロンプトで、和文3件の D4 が改行以外の理由(書体の選択、サイズ、行間)で点を分けるようになるか。英語の3件の点が旧プロンプトから大きく動かないか(動いたら、変更が和文以外にも効いている)。
