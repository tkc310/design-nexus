# 95点への道筋(評価の尺度とその他の手段の検討)

> 2026-11-01 の評価の作り直し(`loop/method.md` の M-017〜M-022)で、この検討から採ったもの(観察できる条件、点の計算、別の系列、参照ページの選び方)と採らなかったもの(部分点と0.5刻み、換算式、D10 のツール判定、モデルの平均)は M-017 に書いた。95点の定義は `eval/rubric.md` の尺度 v2 を正とする。

- **結論**: いまの尺度では 95 点にまず届かない。95 には1ページあたり10観点中7観点で4点が要るが、学習用の審査 416 件でそうなったのは 11 件(9件がケース05)で、各ケースの過去最高点を集めても平均 92.4。止まる原因は、尺度(4点が「目立つ欠陥ゼロ」の関門になり、3と4の判定は審査間で 44% しか一致しない)とページ(狭い幅、デスクトップの空き、組版に実在する傷)の両方にある。
- **尺度の注意**: 0.5刻みにするだけで、ページを変えずに約 +3 点上がる。新しい尺度では 95 を同じ数字のまま使わず、「外部の参照ページと同等」と定義し直す。
- **現実的な目標**: 旧尺度の学習用平均で 92〜93(v0.10.0 の推定 90〜91 から +2 前後)。新尺度では、v0.10.0 と参照ページの差の半分。
- **最初の一手**: eval/runs(git の対象外)を退避し、生成なしで既存のページを使って新尺度を設計・検証する(設計は Opus max、Opus の審査は約 50 件)。並行して M-016 の残りを直し、v0.10.0 の基準点を新旧の尺度で測る。

## 診断

### 材料と数え方

- 理由の分類はキーワードによる粗いもので、件数は目安として読む。

### 1. 95点に要るもの、90前後で止まる形

- **自動の40点は差がつかない。** 169 件中 162 件が満点(平均 39.8)。生成役が同じ lint と render を通して直すためで、95 かどうかは審査の 60 点中 55 点で決まる。
- **55/60 に要る形**: 55/60 は重み付きで 40.3/44。全観点3点(33)からは +7.3 要る。1ページあたり、10観点中7観点が4点(D1 を含む)で、3点未満がない形になる。
- **90 前後で止まる形**: D1・D9 と、D8 か D10 の3観点だけが4点で残り7観点が3点のページは、審査 49.8、合計 89.8 になる。いまの典型がこの形。
  - Opus の審査1件あたりの4点の数は、版とともに増えてから止まった。v0.3.0 で 1.93、v0.6.0 で 3.47、v0.7.1 で 3.39。
  - 増えたのは D1・D9・D5・D10 だった。D6 は全版で0、D4 は 0.07 以下のまま。

- 95 には、ここからさらに +4〜5 要る。これは、これまでの全実験で得た伸びの2倍にあたる。

### 2. 尺度の側

#### 2.1 4点が「目立つ欠陥ゼロ」の関門になっている

- **基準文が全称で書かれている。** 4点の基準文の 10 個のうち7個がそうなっている(「主要な判断すべて」「最後まで」「各幅が」「全状態が」「完全に」「正確」)。反例が1つあれば4点にならない。
- **3点の理由は「よいが、〜」の形をとる。** but・though・; などを含む割合は、3点の理由で 86〜98%(観点別)、4点の理由で 8〜41%(butshape.py)。
- **3点の理由の多くは、4点の基準文を満たしたと書いたうえで、欠陥を1つ挙げる。**
  - D6: 3点の理由の 76% が「余白が 8px の段に乗る」と書く。これは基準文の前半にあたる。74% はそのうえで欠陥を1つ挙げる。
    - 例: 「8px の段に乗り、記録の行の格子をコンソール・形式・表・インストールで使う。形式の節は 1280 と 1920 で、短い logfmt の枠の下に大きな空きを残す」(01、v0.8.1-exp022b、Opus、3点)。
  - D7: 03 の理由はどちらも「Each width is designed:」で始まる。v0.9.0-exp023 は4点だった。v0.8.0-exp020 は「320 の行の強調のむらと、768・320 で『設定』が切れるナビ」で3点だった。
  - D10: 3点の理由の 95% がトークンの一致を書き、68% が小さなずれを1つ挙げる。
    - 例: 「トークン名が文書とコードで違う(accent と --match)。12px の余白が 8px の段の外にある」(01、v0.6.0、Opus)。
- **結論**: 3点と4点を実際に分けているのは、「目立つ欠陥が1つでもあるか」である。これは基準文に書かれていない。

#### 2.2 審査の指示が、そろって点を下げる向きに働く

- 下げる向きの指示は4つある。
  - judge-prompt.md の「4 is rare」。品質の基準ではなく、分布の指示である。
  - 「Prefer the lower score when unsure」。
  - パネルの「ほかの人は下げるだけで、上げられない」。
  - 専門家の拒否権。
- 4人のうち1人が傷を1つ見つければ、3点になる。審査は4幅の全ページの撮影とコードを見るので、傷を見つける機会は多い。
- どれも単独では正しい規則で、甘い審査を抑えるために入れた(M-001)。ただし重なると、尺度の上の方を圧縮する。

#### 2.3 3と4の境界は、審査ごとに揺れる

  - 観点ごとの完全一致は 83%。
  - どちらかが4点のとき、両方が4点なのは 22/35(63%)。D4 の一致は 6/12。
  - 審査点の差は平均 2.2/60、最大 4.8。

  - D6 は完全一致 96% だが、κ は 0.23。一致の理由は「どちらも3点」だからである。
- 4点が付くかどうかは、ページよりも審査の当たり方で決まる部分が大きい。

## 評価の尺度の改善

### 方針

- **尺度を甘くしない。** 分解能を上げ、3点と4点を実際に分けているもの(4点の条件をいくつ満たすか、目立つ欠陥があるか)を基準文に書く。
- **新旧の点を比べない。** 数字の意味が変わるので、95 を定義し直す(後の「95 の再定義」)。
- **採用の判定は、これまでどおり対比較(規則6)で行う。** 新尺度は、進み具合の記録と、95 までの距離を測るのに使う。

### 新尺度(v2)の骨格

1. **条件**: 各観点に、4点の条件を4つ置く。どれも観察できる形で書く。審査は条件ごとに、満たすか満たさないかと、その根拠(幅と要素)を書く。
2. **点**: 点 = 2 + 0.5 × 満たした条件の数(2〜4 の 0.5 刻み)。
   - 現行の2点の文(最低限)に届かないときは、0〜1.5 にする。
   - 点は run.mjs が条件から計算する。審査に足し算をさせない。
3. **欠陥の扱い**を、全観点でそろえる。
   - WCAG 2.2 AA の違反、または読めない・誤読させる欠陥: その観点は2点まで(現行の拒否権のまま)。
   - 目立つ欠陥(最初の画面、見出し、ボタン、ラベルにあるもの、または繰り返すもの): 関係する条件を1つ、満たさないとする。観点全体を3点にはしない。
   - 目立たない欠陥が1件だけ: 記録するだけ。いまは専門家の規則にだけある扱いを、全観点に広げる。
4. **欠陥の持ち主を、1観点に決める。**
   - 狭い幅で切れる・隠れる → D7
   - 和文の改行、数字と単位、小さな文字 → D4
   - 最初の画面の順序、主な操作 → D3
   - 要素の欠け、ブリーフとの食い違い → D1
   - 見慣れた見た目かどうか → D2(D4・D5 では問わない)
5. **面による扱い**
   - プロダクト面(03・04)の D2 は、主な画面(仕事のデータと操作)で決める。ナビ・サイドバー・ヘッダーが慣習どおりなのは減点しない。
   - 静的なページ(02・06)の D8 は、ブリーフが含意する状態(満席、締め切り、送信の検証)で決める。操作が少ないことを減点しない。
6. **パネルの規則**
   - 「4 is rare」を削る。
   - 「迷ったら低い方」は条件の単位で使う(迷う条件は満たさないとする)。
   - 条件は担当のペルソナが決める。ほかの人は、根拠を示せば条件の判定を覆せる(上げも下げも)。拒否権は残す。
7. **D10 の c1・c2 は、ツールで決める。** lint の N09 を EXP-021 の変種の拡張で使い、書体の先頭と動きの時間まで比べる。審査は c3・c4 だけを判断する。
8. **審査の出力**に `criteria`(観点ごとの c1〜c4 の真偽と根拠)を足す。`scores` は計算で出す。

### 観点ごとの条件(2・3・4点の分け方と、4点の例)

例の引用は審査の理由の要約で、括弧はケース・run・審査。

**D1 主題適合(重み 1.5)**

- **4点の条件**
  - c1: ブリーフが求める要素と状態が、すべてあって動く。
  - c2: ページの仕事(1つの動詞)を、1280 と 320 の最初の画面で果たせる。
  - c3: 主な判断(シグネチャ、主なデータの見せ方、文の調子)を、ブリーフの事実か利用者の必要に結びつけて言える。
  - c4: ブリーフにない事実(数字、機能、リンク、評判)を作っておらず、ページに作り手向けの注記がない。
- **2点**: 仕事は果たすが汎用。または、必須の要素が1つ欠ける。
- **3点の典型**: c3 を満たさない例。ページ自身が「ろくろは使わず」と書く手びねりの教室で、シグネチャがろくろだった(02、v0.1.0-exp001、Opus)。
- **4点の例**: 「ブリーフの全項目が 320 で動く。56px の停留所の選択、大きな『あと…分』の次の3本、その日の全時刻表、(本日)を示す平日・土日祝の切り替え、黄色の運休のお知らせ、18px の本文と大きな文字の切り替え」(05、v0.7.0-exp017、Opus)。

**D2 独自性(重み 1.5)**

- **4点の条件**
  - c1: 題材の世界の名指しできる実物(書類、道具、標識、素材)から取ったシグネチャが、1280 と 320 の最初の画面に見える。
  - c2: シグネチャを隠した 1280 の最初の画面が、この分野の既定の見た目と区別できる。既定の見た目とは、開発ツールなら黒地+mono+1色、SaaS なら白いカード+サイドバーなど。プロダクト面では主な画面で判断する。
  - c3: シグネチャの単位や素材が、ほかの2か所以上(見出し、操作部品、表、フッター)で使われる。
  - c4: 借りた印が凡例なしで読め、どの幅でも同じ意味を持つ。
- **2点**: 印象的な要素が1つで、残りは汎用。
- **3点の典型**: c2 を満たさない例。「黄色の検索ヒットの帯がフィルタ・インストール行・結果に繰り返し出て具体的だが、全体は多くの開発ツールと同じ黒地+mono」(01、v0.7.1-exp019、Opus)。
- **4点の例**
  - 「鉄のレール、吊るされた No. 0418 の伝票、ゴム印が、製品の考えそのもの。同じ伝票の言葉が、レールの画面、伝票の裏、ミシン目の登録欄まで続く」(06、v0.7.1a、Opus)。
  - 「検印欄の仕組み。承認行の朱の認印、未承認の点線の『未』、進み具合の小さな印の列。外枠のサイドバーと白いカードだけが標準」(03、v0.9.0-exp023、Opus)。

**D3 視覚階層**

- **4点の条件**
  - c1: 1280 と 320 の最初の視点が、仕事の答えか主な操作になっている。大きさか太さで、1つだけが勝つ。
  - c2: 各幅で、塗りの主な操作は1つ。副の操作は、見て弱いと分かる。
  - c3: 最初の画面より後の節にも、それぞれ焦点がある。同じ重さの節が続かない。
  - c4: 強調の順序が、優先度と一致する。承認済みの行が要対応の行より目立つ、のような逆転がない。
- **2点**: 第1視点は明確だが、2番目以降が曖昧(現行どおり)。
- **3点の典型**: c3 を満たさない例。「ヒーローは見出し→棚→CTA と読めるが、その下の節はどれも同じ小見出しと明朝の h2 で、目立つものがない」(02、v0.3.0、Opus)。
- **4点の例**
  - 「黄色の『あと何分』が紛れもない最初の視点で、次が発車時刻。時刻表は同じ便を同じ黄色で示す」(05、v0.7.1a、Opus)。
  - 「『KNOW WHO HAS IT.』と動く伝票が最初の画面を占め、朱の主ボタンが唯一の塗り。各節に見出しが1つ、仕事が1つ」(06、v0.6.0、Opus)。

**D4 タイポグラフィ**

- **4点の条件**
  - c1: 組み合わせの理由を、題材から言える。表示書体は題材の文字から、本文の書体は読者から選ぶ。書体ごとに役目が1つで、近い書体が重ならない。
  - c2: 文字の大きさは6段以下で、比が一定。読んで判断する文字は 14px 以上(高齢・疲れた読者には 16px 以上)。
  - c3: 数字の扱い。比べる数字は等幅にする。数字と単位を離さない。桁区切りは細い。本文に斜線ゼロがない。
  - c4: 見出し・ボタン・ラベル・最初の画面の文が、4幅のどこでも語の途中で折れない(和文は JLReq と文節で判断)。見出しの最終行が1〜2字にならない。
- **2点**: スケールは健全だが、組み合わせが平凡(現行どおり)。WCAG 級の小ささや、読めなくなる折れは、拒否権で2点まで。
- **3点の典型**: c4 を満たさない例。「公共の標識に合う組み合わせで、16px 未満はなく禁則も守るが、1280 の最初の画面で『運休/します。』と折れる」(05、v0.7.1b、Opus)。
- **4点の例**: 「すべての時刻に BIZ UDGothic の等幅数字、18px の Zen Kaku Gothic New、大きな数字の横の小さな『発』『分』、文節で折れる見出し。折れは目立たない場所(320 のフッター)だけ」(05、v0.6.0、Opus)。目立たない傷が1件あっても4点を妨げない、という新尺度の規則の実例でもある。

**D5 色**

- **4点の条件**
  - c1: 色は4〜6の役割で、1色に1つの意味。「オン」と「保存」で同じアクセントを使わない。状態の色は状態にだけ使う。
  - c2: 各色の出所を、題材の中で言える。
  - c3: 静止・hover・focus・無効のどの状態でも AA を満たし、入力欄などの非テキストは 3:1 を満たす。
  - c4: 色の強さの順が、優先度と一致する。すべてのトグルがアクセント色、承認済みの印が要対応より強い、のような逆転がない。ダークモードがあれば、役割を保つ。
- 記憶に残るかどうかは D2 で問う。「控えめ」「単調」は、D5 の減点の理由にしない。
- **3点の典型**: 「すべての色に役目があり、規律も出所もあるが、単調なほど静か」(01、v0.8.1-exp022a、Opus)。新尺度では、c1〜c4 を満たせば4点になる。
- **4点の例**: 「路線の緑は次のバスと帯に、赤は運休だけに、墨は構造に使い、地はアルミの灰色。役割を保つダークの組もある」(05、v0.8.0-exp021、Opus)。

**D6 レイアウトとリズム**

- **4点の条件**
  - c1: 余白は1つの基準の段に乗る。群の中の間隔が、群の間の間隔より小さい。
  - c2: 節の構造が、内容から決まる(表、手順、1つの大きな図、比較)。同じ枠(小見出し+見出し+導入文)の節が3つ以上続かない。
  - c3: 1280 と 1920 の最初の2画面に、320×256px 以上の空き(EXP-024 の R26 と同じ基準)がない。1920 は、1280 を中央に置いただけではない。
  - c4: 列と基準線が節をまたいでそろい、sticky の列が引き伸ばされない。全ページの撮影に写る固定バーの重なりは数えない。
- **2点**: グリッドは保たれるが単調。または、空きやずれが2か所以上ある。
- **3点の典型**: 2.1 の 01(v0.8.1-exp022b)。c1・c2 は満たし、c3 を満たさない(新尺度では 3.5)。
- **4点の例**
  - Opus と Sonnet の4点はない。Fable の1件は「rem による 8px の段、2px の墨の枠、盤に合わせて伸びる数字、64em からの sticky の列。3列と2列の区画が幅ごとに組まれている」(05、v0.3.0-exp008)。
  - 較正には、対比較で D6 を取った理由を使う。例: 02 の v0.7.1a は「壁の帯と紙の帯を交互にして各節に地があり、タイルの格子(6・4・4・3)が一定のリズムを保つ」。v0.3.0 と v0.7.1b の両方に対して D6 を取った。

**D7 レスポンシブ**

- **4点の条件**
  - c1: 320 で、読む・コピーするもの(コマンド、入力欄の既定値、金額の列、合計のラベル)が切れず、隠れない。主な操作かシグネチャが、最初の画面にある。
  - c2: 768 に独自の構成がある。引き伸ばした電話の形でも、押し込んだデスクトップでもない。表は、収まるうちは表のまま。
  - c3: 1920 で、空間を意図して使う。
  - c4: 幅で意味が変わらない。印・凡例・ラベルはどの幅でも同じ意味で、組み替えでラベルが落ちない。
- **2点**: 動くが、モバイルは後回し(現行どおり)。
- **3点の典型**: c1 を満たさない例。「各幅が設計されている。768 は氏名と職種を1列にし、320 はラベル付きのカードにする。320 の行の強調のむらと、768・320 で『設定』が黙って切れるナビが欠点」(03、v0.8.0-exp020、Opus)。
- **4点の例**: 「各幅が設計されている。1920 は手順と合計を表の横の 2×2 に置く。768 はサイドバーを上部のバーに替え、職種を氏名の下に入れる。320 は各スタッフの行を、差引支給額が先頭のラベル付きブロックにする」(03、v0.9.0-exp023、Opus)。

**D8 状態とインタラクション**

- **4点の条件**
  - c1: ブリーフが名指しする状態と含意する状態が、すべて実際のコードの道筋にあり、到達できる(見本集ではない)。
  - c2: 失敗しても入力が残り、何が起きたかと直し方を言う。当てはまらなくなった結果やトーストは、消すか、古いと示す。
  - c3: 操作部品に hover・focus-visible・active・無効の状態がある。操作の後に focus が移り、必要な読み上げがある。
  - c4: 動きに目的があり、reduced motion で代わりがある。
- **2点**: 主要な状態はある(現行どおり)。
- **3点の典型**: 「席の状態(空き、埋まり、満席と待ち)は実際の部品にあり、ボタンに hover・focus・active がある。静的なページなので、ほかに状態はない」(02、v0.7.1b、Opus)。新尺度では、含意する状態で判断するので、4点になりうる。
- **4点の例**: 「状態が最後まで設計されている。月の切り替えのスケルトン、未作成の月と絞り込みの空、再試行つきのオフラインのエラー、focus の受け渡しとトーストつきの個別・一括承認、ブロッカーへ案内する『まだ確定できません』、取り消しつきの確定ダイアログ」(03、v0.7.1a、Opus)。

**D9 UXコピー**

- **4点の条件**
  - c1: 題材の語彙で書かれ、誇大な句や定型の句がない(R10)。
  - c2: 動詞が一貫する(ボタンとトーストが同じ動詞)。ボタンは、押した結果を約束する。
  - c3: エラーと空の状態が、何が起きたかと次の一手を言う。
  - c4: 比喩の語が操作部品に漏れない。用語と単位の書き方がそろう。
- **3点の典型**: c2 を満たさない例。「具体的で誇大さもないが、主な CTA『Start a rail』は招待の申し込みにつながり、ボタンが約束しすぎる」(06、v0.6.0-exp013、Opus)。
- **4点の例**: 「Push and Slack hold until quiet hours end. Email still arrives.」「Couldn't save: the server didn't respond. Your changes are still here…」(04、v0.6.0、Opus)。

**D10 システム一貫性**

- **4点の条件**
  - c1: 色・大きさ・余白がカスタムプロパティから来ていて、はぐれた値がない(ツールで判定)。
  - c2: DESIGN.md のトークンの値と CSS の値が一致する。色、書体の先頭、動きの時間を比べる(ツールで判定)。
  - c3: DESIGN.md の Patterns に書いた型がコードにあり、消えた型が文書に残っていない。
  - c4: トークンの段(余白、角丸、大きさ)から外れた値がない。
- c1・c2 をツールに任せる理由: Opus と Sonnet の κ が 0.11 しかない。審査がどこまでコードを読むかで揺れるため。
- **3点の典型**: 2.1 の 01(v0.6.0)。c4 を満たさない。
- **4点の例**: 「CSS の値が DESIGN.md のトークン(地、面、罫、アクセント、危険、4px の角丸、8px の余白、1.25 の比)と一対一で一致し、ボタン・パネル・動きの型が書いたとおり」(01、v0.6.0-exp013、Opus)。

**手順**

1. 新尺度を事前に登録する。基準文、計算式、参照ページの選び方、目標の決め方を、新尺度で何かを採点する前に固定してコミットする。
2. 既存のページを採点する(生成は要らない)。

3. 参照ページを採点する(V4)。
4. 判定する。
   - V1〜V4 を満たせば採用し、method.md に M-017 として記録する。
   - 満たさなければ、どの条件で落ちたかを見て基準文を直す。直すのは1回までにする。同じページで直し続けると過剰適合になるので、2回目の確認は v0.10.0 の新しい生成で行う。

### 「甘くしただけ」を見分ける

- **0.5 刻みにすると、ページを変えずに審査点が約 +2.8/60 上がる**(halfpoint.py)。
  - 推定の方法: 3点の理由のうち、4点の基準文を満たしたと書いたうえで欠陥を1つ挙げたものを、3.5 点とした。v0.6.0 以降の 138 件でも +2.8。
  - v0.10.0 が旧尺度で約 90〜91 なら、新尺度の生の点は約 93〜94 になりうる。95 を同じ数字のまま目標にすると、尺度を変えただけで「ほぼ届いた」ことになってしまう。
- **見分け方**: 平均が上がること自体は問題ではない。問題は、上の方の差(v0.3.0 と v0.7.1、v0.10.0 と参照ページ)が広がらないまま、全体が持ち上がること。V1・V3・V4 がこれを測る。
- **やってはいけないこと**: 「4 is rare」を消すだけ、「迷ったら高い方」にする、のような変更は、分解能を上げずに全体を持ち上げるだけ。

### 95 の再定義

1. **新尺度の点は、旧尺度と別の系列として記録する。** history.jsonl と summary に尺度の版を付け、同じ表に並べない。
2. **新尺度で次を測る。**
   - B: v0.10.0(6ケース × 2回、Opus の2回の平均)
   - R: 参照ページ(4〜6件)
   - L: v0.3.0(6件)
3. **95 の線を R に置く。** 表示には次の換算点を使う。B_old は、段階0で測る v0.10.0 の旧尺度の点。

   換算点 = B_old + (95 − B_old) × (s − B) / (R − B)

   換算点では、95 が「参照ページと同等」、B_old が「いまの v0.10.0」になり、見慣れた数字で距離を読める。
4. **R − B が、B の標準誤差の2倍に届かない場合**: 新尺度は上の方を見分けられていない。目標を置かず、尺度を直す。R が B より低ければ、参照の選び方か尺度のどちらかが誤っている。
5. **参照ページを用意できない場合の代わり**: 対比較の勝ち抜きで各ケースの最良のページを選び、人が「このまま出せる」と認めたものを R にする。外部の基準ではないので弱い。記録にもそう書く。

**参照ページの選び方**(事前に決めておく)

- ログインなしで表示でき、render-check(URL を受け付ける)で4幅を撮れる。
- 作りの良さが外部で認められている。たとえば、デザイン賞、デザインシステムの公式の例、広く引用される製品のサイト。
- 01〜06 の面に対応させる。
  - OSS の開発ツールの LP(英)
  - 小さな工房や店のサイト(和)
  - 和文の業務画面(公開デモ)
  - 設定・フォームの画面(英。デザインシステムの例など)
  - 和文の公共交通の時刻表(スマートフォン)
  - チーム向けツールの LP(英)
- ブリーフはページから逆に書き、採点の前に固定する。
- D1 と D10 は比較から外し、D2〜D9 で比べる。D1 はブリーフをページから作るので高く出る。D10 は、参照ページに DESIGN.md がない。
- 審査は同じ手順の Opus で行う。ブランド名は隠せないので、知名度による甘さが入りうる。理由が画面の要素を挙げているかで確かめる。

**到達の見込み**

- **旧尺度の学習用平均**: 段階2〜5 がすべて採用され、効果が足し算になれば 93〜94。過去には、統合した版で効果が再現しなかった例がある(EXP-005・008、v0.4.0 の基準)。それを考えると、現実的には 92〜93。95 に届く見込みは1割程度以下。
- **新尺度の換算点**(95 = 参照と同等): R − B を測るまで分からない。旧尺度で +2 前後の改善は、参照との差の一部しか埋めない見込みが高い。
- **現実的な目標**
  - 旧尺度で 92.5 を次の到達点、93 を上限の目安にする。
  - 新尺度では、参照との差の半分を目標にする。
  - 95 は「参照ページと同等」という長期の目標として残し、このループの到達点にはしない。

## リスクと確かめ方

1. **尺度を変えただけで点が上がる**(+2.8 の見込み)。
   - 確かめ方: 新旧の点を並べない。95 を参照ページで定義する。V1・V3・V4 で、上の方の差が広がったかを見る。
2. **新尺度の条件に、生成役が合わせ込む**(グッドハート)。条件は良いデザインの性質を書いたものだが、条件にない質(驚き、全体のまとまり)が落ちうる。
   - 確かめ方: 採用の判定には対比較(規則6)を残す。版を上げるたびに、参照ページと(できれば)人の点で確かめる。audit.md への導入は、別の仮説として試す(B4)。
3. **条件の判定が甘くなる**(「満たす」と書きやすい)。
   - 確かめ方: 根拠(幅と要素)を必須にする。V2 と較正用の固定ページ(手段 D3)で見張る。条件ごとの「満たす」の率が版の間で急に変わったら、理由を読む。
4. **審査のモデルが日々ずれる、またはモデルが更新される。**
   - 確かめ方: 較正用の固定ページを毎回混ぜる。モデルが変わったら B を測り直す。
5. **生成のばらつき**(ページの標準偏差 約 1.6)で、効果が見えなくなる。
   - 確かめ方: base を2回、候補を2回生成する。絶対点は Opus の2回で記録する。採用は対比較で決める。
6. **効果が足し算にならない**(EXP-005・008)。
   - 確かめ方: 採用するたびに base を作り直す(M-014)。段階ごとに、新尺度の絶対点を記録する。
7. **6ケースへの過剰適合。**
   - 確かめ方: 版を上げた回に、検証用 07〜12 で確かめる。この検討では、検証用の結果を読んでいない。
8. **参照ページを取得できない、または取得しても条件がそろわない**(ネットワーク、Cookie のバナー、重い JS、知名度による甘さ)。
   - 確かめ方: 取得できなければ、代わりの R(対比較の勝ち抜き+人の確認)を使い、そう記録する。理由が画面の要素を挙げているかを読む。
9. **eval/runs が消える**(git の対象外。新しいセッションでは消える)。
   - 確かめ方: 段階0で退避する。撮影の撮り直しはフォントの読み込み(CDN)に左右されるので、撮り直した後に旧の撮影と見比べる。
10. **費用と時間**: 段階0〜4 で生成は約 40〜50 件、審査と対比較は約 150 件になる。同時に動かすのは4体程度なので、延べ約 50 波かかる。
    - 確かめ方: 段階1までで止めても、尺度の診断と v0.10.0 の基準点は残る。各段階の後に、続けるかを判断する。
