# 評価ルーブリック

design-nexus の出力を採点する基準です。改善ループ(`loop/IMPROVEMENT.md`)、審査エージェント、人のレビューで同じ基準を使います。スキル内の `references/audit.md` と同じ10次元です。

尺度は2つあります。**v2**(M-017 以降。40個の観察できる基準、`eval/judge-prompt-v2.md`)と、**v1**(下の「尺度 v1」。M-016 までの記録)です。v2 と v1 は別の系列で、足したり平均したり比べたりしません。

## 尺度 v2(M-017)

審査は点を付けません。40個の基準(各次元4つ)の一つずつに「満たす/満たさない」と根拠を返し、点は `run.mjs` が計算します。

- **次元の点** = 満たした基準の数(0〜4)。拒否権の欠陥(WCAG 2.2 AA を満たさない、または読めない・誤読される)がある次元は2点が上限。
- **v2** = 100 × Σ(重み × 次元の点) ÷ (4 × Σ重み)。重みは v1 と同じ(D1・D2 が 1.5、ほかは 1)。**sub** は D2〜D7 と D9 だけの同じ計算(参照ページと比べるとき)。
- 基準1つの重さは、重み1で 2.27 点、D1・D2 で 3.41 点。
- 自動の部分(lint とレンダーチェック)は足しません。v1 の自動40点は169ページ中162ページが満点で、差を作っていませんでした。Floor はゲートのまま(1件でも不合格)で、ツールの結果は審査が事実として使います。
- **欠陥の重さ**: veto、prominent(第1画面、見出し、ボタン、ラベル、ナビ、表の見出し、主要データ)、repeated(2か所以上)は基準を落とします。minor(1か所の小さな傷)は記録するだけです。1つの欠陥は1つの基準にだけ数えます(どの基準かはプロンプトの対応表で決まる)。
- **主審査のモデル(現在 Opus)の点だけを v2 とします。** 同じモデルの複数回(`judge-v2.opus.json`、`judge-v2.opus.2.json`)は平均します。ほかのモデル(Sonnet、人)は別の系列として記録し、混ぜません。モデルで厳しさが違うためです(v1 で Opus と Sonnet のページ単位の相関は 0.42)。

### 95点の意味

- **95以上 = 拒否権がなく、満たさない基準が重み1で2つまで**(D1・D2 の基準なら1つまで)。100 は40基準すべてを満たす。
- これは「この審査モデルとこのプロンプトのパネルが、挙げた種類の欠陥を2つまでしか見つけない」という意味です。ページの普遍的な品質ではありません。外から見た意味は、参照ページ(V4、`eval/reference/README.md`)と比べてだけ与え、換算式は作りません。
- 平均点だけでなく、目標(92)以上と95以上のページ数を見ます(`summary.md` と history.jsonl の `at_92`・`at_95`)。

### ループの目標は v2 で 92(旧尺度の95点相当、M-023)

- 旧尺度の目標95点は、自動の40点がほぼ満点だったので、中身は「審査 55/60」でした。審査の部分の 91.7% にあたり、v2 ではおよそ **92** です。ループの目標はこの水準に置きます。v2 で 95 は旧尺度の約97にあたり、元の目標より高い水準です。
- **92以上 = 拒否権がなく、満たさない基準が重み1で3つまで**(D1・D2 の基準を含むなら、D1・D2 の1つと重み1の2つ、または D1・D2 の2つまで)。重み1の基準を4つ落とすと 90.9 です。
- **旧尺度への換算(目安)**: 旧 ≈ 40 + 0.6 × v2。自動の40点が満点で、審査の割合が v2 と同じと仮定した近似で、過去の目標と並べて読むためだけに使います。v1 の実際の点と比べたり、採否に使ったりはしません。`summary.md` は v2 の平均にこの換算を添えます。

### 系列と、モデルが変わったとき(M-022)

- v2 の系列は(主審査のモデル、`judge-prompt-v2.md` の版、撮影方法)の組で決まります。プロンプトの版は `JUDGE_PROMPT.v2.md` の先頭に書かれ、score.json と history.jsonl に残ります。`compare --scale v2` は、base と候補で組が違うと警告します。
- **審査のモデルかプロンプトを変えたとき**: 新しい系列を始めます。drift の4ページ(できれば較正セット全体)を新しい審査で採点し(`calib --tier drift` → `validate --against <前の較正 run>`)、ずれを記録します。新しい審査が厳しければ、同じページでも点は下がります。古い系列の数字と直接比べません。
- **生成のモデルを変えたとき**: 版の差とモデルの差が混ざります。同じスキルの版を新しいモデルで2回生成し(スキルを凍結した対照)、旧モデルの base との差をモデルの効果として記録してから、新しいモデルの base でスキルの実験を続けます。run.json の `generator` は history に残ります。
- 基準はほかのページとの比較ではなく観察できる条件なので、生成が良くなれば v2 は上がり、上限 100 まで余地があります。審査のモデルが良くなると、欠陥を多く見つけて v2 が下がることがあります。だから審査の変更は較正ページで切り分けます。

### 較正と検証(M-018)

- 較正セット `eval/calib/v2-validation.json` は、過去の run の学習用ページ45件(コア36、追加9)を `eval/calib/pages/` に凍結したものです。v1 の点と対比較の判定は `v2-validation.evidence.json` にあります。eval/runs は git に入らないので、新しい環境でも同じページで測れるようにしています。
- `calib` は盲検の run を作ります(フォルダ名は `<ケース>--cNN`。どのページかは `_calib/key.json` にだけある)。
- `validate` の検証と目標(採点の前に決めた。結果を見てから変えない):
  - **V1 既知の差**: v0.7.1 が v0.3.0 より高い(Opus の対比較で10勝2敗)。ケースごとの差の平均が正で、d_z ≥ 0.5。
  - **V2 再審査**: 12ページを Opus で2回審査する。基準の一致 ≥ 85%、1回の審査の SD ≤ 3.5点、ケース内の信頼性(1 − 誤差² ÷ ケース内のページの分散)≥ 0.6。v1 は再審査の相関が 0.27 でした。
  - **V3 対比較との一致**: 対比較で clear に決まったページの組で、v2 の差の向きが合う割合 ≥ 75%(差が 0.5 点未満は半分と数える)。v1 も点を持つ組では、v1 より低くないこと。
  - V4 参照ページ(ネットワークが要る)と V5 人の審査(`v2-template`)は任意で、参考にする。
- 外れたら `judge-prompt-v2.md` を1回だけ直し、直すのに使わなかったページ(新しい生成)で確かめ直します。

## 審査パネル

審査は「熟練デザイナー4人のパネル」として行います(`eval/judge-prompt.md`)。担当する次元を持つ人が点を提案し、ほかの人は具体的な理由があるときだけ下げられます(上げることはできません)。

| ペルソナ | 主担当 |
|---|---|
| ブランド・ビジュアルのデザインディレクター | D2・D4・D5 |
| プロダクト・インタラクションデザイナー | D1・D3・D8・D9 |
| レイアウト・フロントエンドのデザインエンジニア | D6・D7・D10 |
| アクセシビリティ・ローカライズの専門家 | 全次元に拒否権。WCAG 2.2 AA を満たさない欠陥、または内容が読めない・誤読される欠陥があれば、その次元は2点が上限。組版の小さな傷は、目立つ場所か繰り返しのときだけ1点下げる。和文の改行は JLReq で判断する(本文の仮名・漢字の間の改行は正しい組版。禁則違反、数字と単位の分離、見出し・ボタン・ラベルでの語の分割、見出しの1〜2字の最終行が欠陥) |

## 審査モデルの役割

- **主審査(最終判定)**: 最も厳しい1モデル(現在は Opus)。採用判定では、主審査の平均が −1 点を超えて下がったら不採用にする。甘い審査を混ぜた平均で、主審査が見た悪化を隠さないため。
- **並列審査**: ほかのモデル(現在は Sonnet。Fable はトークン消費が大きいため、v0.4.0 の基準以降は使わない)。同じモデルの採点を繰り返したとき(`judge.<モデル>.<n>.json`)は、まずモデルごとに平均し、各モデルを1票として数える。主審査と同じパネルで採点し、3者の平均を合計点に使う。審査ごとの差は、甘さの偏りを見るために必ず記録する。
- 生成と計画も、主審査と同じ最上位モデルで行う。スキルの上限を測るため。

## 学習用と検証用のケース

- `split: train` のケース(01〜06)だけを見て仮説を立て、実験の判定にも使う。
- `split: holdout` のケース(07〜12)は改善には使わない。数回の実験をまとめて終えたときにだけ、その回の最初と最後で比べる。学習用だけが伸びて検証用が伸びないなら、この6件への過剰適合を疑う。

## 採点のルール

- 各スコアには根拠を1文で書く(どの画面・要素を見たか)。
- 迷ったら低い方を付ける。2 は「問題はないが良くもない」。
- スクリーンショットが無いときは D7 を「n/a」とし、配点から除いて換算する。
- 審査者は生成したエージェントと別のコンテキストで実行する(生成者は自分の判断を正当化しやすいため)。

## 採用判定(改善ループ、v1)

v2 の検証(V1〜V3)が通るまで、または通らなかったときに使います。通ったあとは、下の「採用の手順」を使います。スキルの変更案は、ベースラインと同じケースで比較して次をすべて満たすときだけ採用します。

0. 比較の前に、base を現在のチェックで採点し直す(`compare` が自動で行う)。
   base は、同じ版の生成が2回以上あればケースごとに平均する(`compare --base 走行1,走行2`)。生成1回のばらつきは、6件平均で約3点ある(M-005)。
1. 新たな Floor 不合格ケースが出ていない。
2. 全ケース平均の合計点がベースライン以上(審査のゆらぎを考え、−1点までは同等とみなし、その場合は狙った次元が +0.5 以上改善していること)。
3. どのケースも −5点を超えて悪化していない。
4. 変更が狙った次元・チェックIDで改善が見られる。
5. 主審査の平均が −1 点を超えて下がっていない。主審査の差が −1〜−2.5 点の境界にあり、ほかの条件をすべて満たすときは、base と候補の両方で主審査をもう1回ずつ別のコンテキストで採点し(`judge.opus.2.json`)、2回の平均で判定し直す。1回の採点のぶれ(6件平均で約1点)で、狙いどおり効いた変更を捨てないため。
6. 境界の候補は対比較で判定する(M-008)。合計の差が −1.5〜+1.5 点のとき、または規則2・5と、対比較で代わりに確かめられる規則4だけで落ちるときは、規則2・5の代わりに次を使う。候補の run で `pair --base <base run>` を作り(base が2回なら両方)、主審査 Opus が片順で審査する。`pair-score` の「clear only」(margin が slight の判定は引き分け)で、勝ち − 負け が対の数の 1/4 以上(切り上げ。6対なら +2、8対なら +2、12対なら +3)で採用、0 以下で不採用、その間は候補をもう1回生成し、base との対を足して同じ基準で判定する(M-015。Sonnet は審査の癖を調べるときだけ使う)。候補を2回生成したときは、両方の run の対を合わせて数える。規則1・3・4は対比較でも満たす(規則4は、対比較の狙った次元の勝ち − 負け が +1 以上でもよい)。守る次元は仮説が予想する失敗の2〜3個に絞り、その net が対の数の −1/2 以下か、同じ次元を決め手にした clear 負けが2件以上のときだけ不採用にする。−1/4〜−1/2 は「要観察」として記録する(M-013)。base は採用した候補 run ではなく、その版で新しく生成した2回にする(M-014)。

## 採用の手順(M-021、v2 の検証が通ったあと)

規則0〜6の考え方(Floor はゲート、対比較の clear only、守りの絞り込み、選ばれていない base、保留域は新しい生成)は変えず、v1 の平均点の規則(2・3・5)を v2 の見張りに置き換えます。

- a. base は、いまの版で新しく2回生成した 01〜06(M-014)。v2 で Opus が各ページを1回審査する(プロンプトを直した直後は2回ずつ審査し、再審査のぶれを新しいページで測り直す)。
- b. 候補は1回生成する。仮説の対象が一部のケースでも、6ケースすべてを生成する(ほかのケースの悪化を見るため)。候補も v2 で1回審査する。
- c. 新たな Floor 不合格があれば不採用(規則1)。
- d. 対比較: `pair --base <base の run をすべて、カンマ区切り>` で、各ケースを2つの base と組んだ12対を作り、Opus が片順で審査する。`pair-score` の clear only の 勝ち − 負け が ⌈対の数 ÷ 4⌉ 以上(12対で +3)なら次へ、0 以下なら不採用、その間は候補をもう1回生成して対を足す(24対で +6、M-015)。
- e. 守る次元(仮説が予想する失敗の2〜3個)の net が −対の数 ÷ 2 以下、または同じ次元を決め手にした clear 負けが2件以上なら不採用(M-013)。
- f. `compare --scale v2` が HOLD(v2 の平均が 2SE を超えて低下)を出したか、どこかのケースに新しい拒否権が出たら、その基準の根拠を読む。根拠が同じ具体的な欠陥を指していれば不採用、ばらばらなら対比較の判定に従う。v2 の差と動いた基準は、どちらでも `loop/experiments.md` に書く。
- g. 採用したら版を上げ(AGENTS.md)、新しい版で base を2回生成し直す(M-014)。検証用 07〜12 は回の区切りでだけ使う。

### 経路 P と経路 C(M-025)

仮説を書くときに、経路を先に決めます。両方の計器(v2 の基準と満たす率、対比較の次元と決め手)の予想も書きます。

- **経路 P(対比較)**: 上の a〜g。ただし d の段階2(+1・+2 で生成を足す)は、守る次元のどれも −対の数 ÷ 4 以下でないときだけ行う。どれかが −対の数 ÷ 4 以下なら、段階1で不採用。
- **経路 C(基準)**: v2 の衛生の基準(対比較の決め手にならない欠陥)を狙う変更に使う。次をすべて満たせば採用。
  1. 新しい Floor がなく、どのケースにも新しい拒否権がない。出たら f のとおり根拠を読む。
  2. ツールがある場合は、ツールが出る候補のページが6ページ中1以下で、base の12ページでは4ページ以上に出ている。
  3. 狙った基準(先に決めた1〜6個)を合わせた満たす率の上がり幅が、min(0.3, base の不合格の率の半分) 以上。ツールがなければ、候補を2回生成した12ページで測る(1回目の6ページで届かなければ、2回目を作らずに不採用)。
  4. 害がない(1回目の12対): clear only の net が −2 以上、守る次元(2〜3個)がそれぞれ −対の数 ÷ 2 より上、変更そのものを決め手にした clear 負けが1件以下。
  5. `compare --scale v2` で HOLD がない。狙った以外で満たす率が 0.5 以上下がった基準があれば根拠を読み、同じ具体的な欠陥を指していれば不採用。
- 両方の条件を満たしたら、経路 P として記録する。版は、ツールだけの変更が patch、本文の規則の変更が minor。
- v2 の審査は盲検で行う(`judge --scale v2 --blind`、M-026)。V3 の一致が 75% 未満と分かったら、経路 C はツールのある基準に限る(M-027)。
